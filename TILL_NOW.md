## ⚠️ Known problems / limitations
- This hardware (RTX 4060, 8GB VRAM) is slow for larger-context LLM calls on a 9B model. Service 2 now runs with **one** bounded section-revision round (`FAST_REVIEW_CONFIG.max_section_revision_rounds=1`, changed from 0 in D-020) — full-document revision (`max_full_revision_rounds`) remains 0 for this reason. See DECISIONS.md D-010/D-020.
- Leaf-section writing reliability in Service 2 is now well-verified: the `TAG-ROOT` overlap, the container-content crash, disabled revision rounds, and the citation-boundary false-positive bug are all fixed (D-019/D-020/D-021) — 3 consecutive real stress runs across 3 different topics (including the two previously-problematic ones) all reached `draft_status: "complete"` with every section resolving on its first attempt. This is not a claim of zero future failures on a 9B local model (irreducible variance remains), but the specific diagnosed bugs are closed and verified not to recur — see `analytics_and_results.md` §12.
- Failures still surface honestly via `WritingResult.draft_metadata.warnings`/`errors`/`draft_status` and are reflected in Service 4's `process_control` score, not hidden, on the rare occasion one does occur (e.g. "insufficient evidence" for a tag, or a bookend section being replaced after failing its own evidence-context audit — both correctly-functioning safety behavior, not defects).
- Service 1's relevance gate (D-018) is deterministic token/phrase overlap, not semantic understanding — it cannot distinguish two genuinely different meanings that happen to share a word. This is a documented, accepted limitation, not a defect; it closes the specific failure mode actually observed (zero topical overlap).
- Service 3 only checks the reference list, not positional in-text citation markers against the draft body — a documented scope decision (DECISIONS.md D-012), not a defect.
- Service 4's claim-to-evidence check depends on Service 3's extracted DOI matching a Discovery record; when Service 2's own leaf-section reliability issue leaves a draft with very few real citations (as in the live full-pipeline run — only 1 of the corpus's papers actually got cited), Service 4 has correspondingly little to check. This is expected given Service 2's known limitation, not a Service 4 defect.
- Semantic Scholar / OpenAlex-based verification searches intermittently fail with rate-limit-style errors in testing; the pipeline degrades gracefully in both cases.
- Recurring test-isolation issue: every pipeline service's entry point is named `service.py` and reached only via `sys.path` insertion, so a bare `import service` in a test file silently reuses whichever service module another test file imported first in the same pytest session. The orchestrator now imports all four in one process via `importlib.util.spec_from_file_location` under unique names up front (`orchestrator/pipeline.py::_load_service()`), which is also the fix pattern used per-test-file elsewhere; no longer purely an ad hoc per-occurrence patch now that the orchestrator centralizes it, though the test files still each do their own loading too.
- **Gemini provider**: a real security bug was found and fixed (D-023) — the API key leaked into tool output via URL-embedded query-parameter error chaining during the one live test attempted. Fixed (header-based auth, suppressed exception chaining, 2 regression tests); **a full successful research draft generated via Gemini has still not been observed** — the live test was halted for safety after the key exposure, before the original question (does content generation work) was answered. Needs a fresh, valid key to close.
- **Ollama automatic installation (missing-machine path)**: genuinely verified via Docker isolation for detection + the Linux safety-refusal guidance (D-024) — real, not mocked. Windows/macOS `winget`/`brew` install commands remain verified only via mocks (this dev machine already has Ollama; no Windows/macOS machine without it was available).
- **PDF compilation**: genuinely verified both via Docker isolation (D-024) and, since then, directly on the host machine — `tectonic` is now installed locally (`C:\Users\owais\bin\tectonic.exe`) and has produced real, valid PDFs (including both IEEE/`IEEEtran` and Springer/`llncs` document classes — D-026) across multiple real pipeline runs. `pdflatex` specifically remains untested (only `tectonic` has ever been used).
