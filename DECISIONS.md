## D-018 — Root-cause fix: Research Discovery had no relevance signal against the actual research question
- **Date:** 2026-08-28
- **Problem:** A known failure (TILL_NOW.md, D-011's footnote) selected an asthma-management guideline for an intermittent-fasting/cognition query. This reliability pass required diagnosing the actual root cause rather than patching that one example.
- **Root cause, confirmed by reading `discovery/pipeline.py::rank()` line by line:** the ranking function that decides the final 6-9 paper corpus had **zero signal comparing a candidate paper to the research question**. It scored purely on: abstract presence (+4), `log(citations)` capped (+4.8 max), recency (+2 max), and the paper's position in the search engine's own result ordering (+4 max, i.e. `relevance_rank` — a field that, despite its name, is just "how far down OpenAlex/Semantic Scholar/etc. returned this result," not a measure of relevance to the user's question). Combined with `analysis.py`'s own query-generation prompt explicitly instructing "favor recall over precision... broad terms beat narrow exact phrases," a search can legitimately return marginally-related or spuriously-matching papers, and nothing downstream ever re-checked them against the actual question before they entered the corpus. A recent, well-cited, abstract-bearing paper could win purely on those grounds regardless of topic. This is not a search-engine bug or an LLM hallucination — it is a straightforward missing validation step.
- **A second, related bug found during this diagnosis:** `services/research-discovery/service.py::run_discovery()` built a `DiscoveryRequest` with a `keywords` field but never passed it to `discovery/pipeline.py::run_pipeline()` — user-supplied keywords were silently dropped and never influenced search or ranking at all.
- **Fix — `services/research-discovery/discovery/relevance.py` (new):** a deterministic (no extra LLM call) hard relevance gate run after dedupe and before ranking:
  - `build_topic_profile()` extracts significant unigrams and bigrams from the research question, the LLM's own generated `keyword_query`, and any user-supplied keywords (now actually wired through — the second bug above is fixed as part of this).
  - `score_paper()` compares each candidate's title+abstract+venue against that profile: unigram overlap ratio, a bonus for shared meaningful two-word phrases (a much stronger signal than lone-word overlap — this is what lets "intermittent fasting" as a phrase count for more than either word alone), and a bonus for overlap specifically with the highest-confidence terms (user keywords + the LLM's own keyword query, not just the loosely-worded raw question).
  - **Hard gate:** a paper scoring below `HARD_REJECT_THRESHOLD` (0.12) with no shared meaningful phrase is rejected outright — it never reaches ranking, regardless of citations or recency. `screen_papers()` splits the deduped candidate set into accepted/rejected and annotates every `Paper` with `relevance_score`/`relevance_decision`/`relevance_reason` for transparency.
  - **Ranking change — multiplicative, not additive:** `rank()` in `discovery/pipeline.py` was changed to multiply the existing citation/recency/abstract/search-position score by `relevance_score`, not add it as a bonus term. An additive bonus was tried first and failed its own adversarial test (see below) — a highly-cited, recent paper with only weak topical overlap could still outscore a genuinely on-topic paper because the other signals summed to more than the relevance bonus could offset. Multiplying means a paper's citation/recency "quality" only counts for as much as it is actually relevant to begin with.
  - If a research question genuinely yields zero relevant candidates, `run_pipeline()` now raises `PipelineError` explicitly rather than silently forcing the corpus down to size 0 or backfilling with rejected papers — the corpus is allowed to end up smaller than `corpus_size` when fewer than that many papers are genuinely relevant (this was already tolerated by the existing discovery integration test's `1 <= len(selected_papers) <= corpus_size` assertion), but it is never padded with known-irrelevant filler.
  - A new `relevance_filter` progress event reports accepted/rejected counts and up to 5 example rejections (title, score, reason) for operator visibility.
- **Known, documented limitation (not hidden):** this is deterministic token/phrase overlap, not semantic understanding — it cannot distinguish two genuinely different meanings that happen to share a word (e.g. "fasting" in a pre-surgical-protocol paper vs. an intermittent-fasting-diet paper). Closing that fully would need embeddings or an LLM judgment call per candidate paper, which is deliberately out of scope per the "don't require expensive LLM calls if deterministic checks are sufficient" instruction for this pass, and per this hardware's existing LLM-call bottleneck (D-009). What this fix guarantees is narrower and matches the actual observed bug: a paper sharing no meaningful terms or phrases with the topic can no longer enter the corpus, and among papers that do share real topical content, a merely keyword-adjacent one cannot out-rank a genuinely on-topic one on the strength of citations/recency alone.
- **Alternatives considered:** An LLM relevance-judgment call per candidate paper (the spec's own "Stage 4: LLM Relevance Judgment") — rejected for this pass; deterministic overlap already catches the actually-observed failure mode (zero topical overlap) at effectively no cost, and adding one more local-model call per candidate (potentially dozens of candidates before the corpus_size cutoff) would meaningfully slow an already slow pipeline stage for a case current tests don't show is needed. Can be added later as an additional stage if the deterministic gate proves insufficient on more research questions. An additive relevance bonus instead of a multiplicative one — tried first, rejected because it failed the adversarial ranking test (see D-018 test suite, `test_e_adversarial_keyword_overlap_alone_cannot_win_ranking`).
- **Tests:** `tests/services/test_discovery_relevance.py` — 8 tests covering: a clearly relevant paper (accepted), the exact reproduced bug scenario (an unrelated paper rejected), a partially-related paper (accepted but scored below a direct hit), an ambiguous single-keyword paper that must not outrank a genuinely relevant one despite higher citations/recency, an adversarial keyword-overlap paper that must not win ranking despite very high citations, `screen_papers()` splitting and annotating correctly, user-supplied keywords strengthening a match the raw question alone would miss, and a degenerate/empty topic profile not blocking the pipeline. `tests/services/test_discovery_pipeline_integration.py` (live) now also asserts every paper in a real, live-searched corpus has `relevance_score >= 0.12` — i.e. that the gate is actually active end-to-end, not just at the unit level.
- **Impact:** `discovery/pipeline.py::run_pipeline()` gained an optional `keywords` parameter; `services/research-discovery/service.py` now passes `request.keywords` through (previously silently dropped). `Paper` (models.py) and `PaperMetadata` (shared/contracts/discovery_contract.py) gained `relevance_score`/`relevance_decision`/`relevance_reason` fields (additive, backward compatible — default values preserve existing behavior for any code not yet relevance-aware).

## D-019 — Root-cause fixes: Research Writing section/card failure recovery
- **Date:** 2026-08-28
- **Problem:** Service 2's known limitation (D-011) is that typically only 2 of 4 leaf sections succeed per run on this hardware, most often because the model duplicates a point across an ancestor and descendant tag during literature-card extraction. D-011 diagnosed this but explicitly deferred fixing the retry behavior itself ("not fixing further for now"). This pass revisits it as instructed: not by adding more retries, but by fixing what the existing retries actually do.
- **Root cause, confirmed by reading `writing/graph.py`:** two separate retry loops existed, and both were **blind** — an exact, unmodified repeat of the identical request that had just failed:
  1. `build_card_worker`'s literature-card retry (`for attempt in range(1, max_card_attempts + 1)`): on a validation failure (e.g. "point duplicated across ancestor and descendant tag" from `card_validation.py::validate_literature_card`), attempt 2 called `build_literature_card()` again with the exact same `review_question`/`tag_definitions`/`paper_markdown` — nothing told the model what it had gotten wrong the first time.
  2. `write_next_section`'s outer section-attempt retry (`for section_attempt in range(1, max_section_attempts + 1)`): on any exception from `write_section_with_revisions()`, the entire call was retried from scratch with the same context.
  - By contrast, the *inner* revision loop inside `write_section_with_revisions()` (in `section_writer.py`) was already correctly designed as a targeted retry — it passes the specific `SectionAudit.revision_instructions` from the failed attempt into `revise_section()`'s prompt. This had never been unit-tested in isolation before (only exercised indirectly through the full live graph), so its correctness had not been directly verified.
- **Fix 1 — targeted literature-card retry:** `build_literature_card()` (`writing/modules/literature_card.py`) gained an optional `previous_errors: list[str] | None` parameter; when supplied, it is added to the model's prompt payload as `previous_attempt_errors`. `writing/graph.py::build_card_worker` now passes the accumulated `attempt_errors` from prior attempts into the retry call, and `writing/prompts/build_literature_card.md` gained an explicit instruction section telling the model to fix those specific reasons (most commonly the ancestor/descendant duplication D-011 identified) rather than regenerating from scratch.
- **Fix 2 — explicit complete-vs-partial draft classification:** the writing graph's `ReviewResult` already computed a `succeeded` flag and a `failed_tag_ids` list, but neither reached `WritingResult`/`DraftMetadata` at all — a pipeline consumer had no direct way to know whether a draft was complete without re-deriving it from `warnings`/`errors` text. `shared/contracts/writing_contract.py::DraftMetadata` gained `total_sections`, `failed_sections`, and an explicit `draft_status: Literal["complete", "partial"]` field, computed in `services/research-writing/service.py` from `result.succeeded and failed_sections == 0` (both signals must agree; neither is trusted alone). `services/quality-assurance/service.py::compute_scores()` was updated to use this explicit signal (and the actual failed/total section fraction) for its `process_control` score instead of only checking whether any warning/error text exists at all — a draft with 1 of 8 sections failed now scores measurably better than one with 6 of 8 failed, which the old presence-only check could not distinguish.
- **Verification of the already-correct inner revision loop:** added direct unit tests (previously this logic was only exercised indirectly through a full, slow, live graph run) proving: (a) a section with genuinely no evidence returns an honest "insufficient evidence" warning without calling the model at all (no hallucination, no wasted call); (b) a draft that cites a paper outside its allowed list is caught by the deterministic audit and the revision call is actually given that audit's specific instructions (`"Remove citations outside the allowed paper list: P999"`), not a blind repeat; (c) a section that still fails every revision round is explicitly marked `resolved=False` with `unresolved_issues` populated — never silently accepted as a success.
- **Reason:** Per this pass's explicit instruction, "a retry should change something meaningful" and "do not repeat the exact same failed request multiple times without modification" — the literature-card retry was doing exactly that, and had been explicitly flagged as a known gap in D-011 ("not fixing further for now"). The completeness classification directly answers "the system must clearly distinguish COMPLETE DRAFT from PARTIAL DRAFT" using data the graph already computes but never surfaced.
- **Alternatives considered:** A fully separate "fallback generation path" with a simpler prompt/smaller context (the spec's own suggested layered strategy) — deferred for this pass; the targeted-retry fix directly addresses the empirically diagnosed root cause (D-011's exact failure mode) with much lower risk of destabilizing a vendored, already-hard-won-stable graph (D-010/D-011) than restructuring its generation strategy further. Rewriting the graph's revision loop from scratch — rejected; it was already correctly designed (uses audit-specific instructions), just never unit-tested; verifying and documenting it was higher-value than replacing it.
- **Tests:** `tests/services/test_writing_literature_card_retry.py` (3 tests, no Ollama required — a fake `LanguageModel` records its prompts): first attempt has no `previous_attempt_errors` key; a retry with errors carries them into the prompt verbatim; an empty error list is treated as no prior attempt. `tests/services/test_writing_section_reliability.py` (3 tests, no Ollama required): missing-evidence sections skip the model call entirely; an invalid-citation draft is corrected via one targeted revision (not two blind attempts) and the exact revision instruction is asserted; a section that never recovers is explicitly `resolved=False`.
- **Impact:** `writing/modules/literature_card.py::build_literature_card()` signature is backward compatible (`previous_errors` defaults to `None`). `shared/contracts/writing_contract.py::DraftMetadata`'s new fields are additive with safe defaults (`total_sections=0`, `failed_sections=0`, `draft_status="complete"`), so existing code paths that don't set them are unaffected.
- **Real full-pipeline verification (2026-08-28, see `analytics_and_results.md` for full detail):** the targeted retry is confirmed mechanically active in a live run — a paper (P003) whose card failed validation on attempt 1 produced a genuinely different (not identical) set of duplicate-point errors on attempt 2, proving the model actually responded to the fed-back errors rather than repeating itself. However, it did **not** fully resolve this paper: nearly every point was still flagged as duplicated across `TAG-ROOT` and a child tag on both attempts. Investigating `tag_definitions.json` from that run revealed a more precise root cause than D-011's original "occasional mis-tagging" framing: `TAG-ROOT`'s own `include_when` criteria are defined as broadly as the entire research question ("addresses both the intervention and the outcome"), so they legitimately overlap with almost every child tag's criteria — making this duplication at least partly **systematic**, not random. `draft_status` correctly reported `"partial"` (2/5 sections, 3 failed) for this run, confirming Fix 2 works correctly end-to-end. A separate, previously-unseen failure also surfaced in this same run: one section hit a `SectionDraft` `ValidationError` (empty-string content) that bypasses the inner audit/revision loop entirely, caught only by the outer, still-blind `max_section_attempts` retry in `write_next_section` — that outer retry was deliberately not touched in this pass (see "Alternatives considered" above) and remains the next highest-value target if this area is revisited. Fixing the root-tag-semantics issue would mean changing `define_tag_semantics.md`'s prompt to explicitly instruct the root tag to exclude anything a child tag already covers — judged out of scope for this pass's risk budget (a different, less-tested part of the vendored graph) and left as a documented follow-up rather than attempted under time pressure.

## D-002 — Local AI model selection: qwen3.5:9b
- **Date:** 2026-08-26
- **Decision:** Use `qwen3.5:9b` (6.6GB) via Ollama as the default local reasoning/generation model.
- **Reason:**
  - Machine hardware: Intel i7-13700HX (16 cores/24 threads), 16GB system RAM, NVIDIA RTX 4060 Laptop GPU with 8GB VRAM (verified via `nvidia-smi`).
  - qwen3.5:9b (6.6GB) fits comfortably within 8GB VRAM with headroom for context.
  - Larger variants (qwen3.5:27b ≈17GB, qwen3.5:35b ≈24GB) exceed available VRAM and would require heavy CPU offload on a 16GB-RAM machine, making development unusably slow.
  - Verified via web search against the live Ollama library (not guessed) that `qwen3.5:9b` is a real, currently published tag.
- **Alternatives considered:** qwen3.5:27b/35b (rejected — hardware too small), a non-Qwen family (rejected — doc specifies Qwen 3.5 family as preferred starting point and it is available and fits).
- **Impact:** All four services call the local model through an `LLMProvider` abstraction defaulting to `qwen3.5:9b`; swapping models later requires no service code changes.
- **Installation command:** `ollama pull qwen3.5:9b`
- **Verification result:** Confirmed working 2026-08-27. `ollama run qwen3.5:9b "Reply with exactly: OK"` responded correctly (model shows a visible reasoning trace before its answer, then replied "OK"). Download took far longer than expected (~24h) due to two compounding environmental issues on this machine, unrelated to the model choice itself — see D-008.

## D-008 — Ollama model storage moved to D: drive
- **Date:** 2026-08-27
- **Decision:** Set `OLLAMA_MODELS=D:\ollama_models` (persisted as a Windows user environment variable) instead of the default `C:\Users\<user>\.ollama\models`.
- **Reason:** The `qwen3.5:9b` pull repeatedly failed/stalled over many hours. Initial diagnosis suspected network throttling by the Killer Wi-Fi adapter's traffic-shaping software (confirmed as a contributing factor — `curl` to the same registry URL was consistently faster than `ollama.exe`'s own download). However, the actual failure was a `curl exit code 23` (disk write failure): the C: drive was completely full (0 bytes free at the time), which silently truncated every download attempt regardless of network speed. This was the root cause; the network throttling only made the symptom slower to diagnose.
- **Alternatives considered:** Freeing up space on C: instead — rejected as fragile; C: was at 98% capacity independent of this project, so any future model pull would risk hitting the same wall. D: has 52GB free, comfortably enough for this and future models.
- **Impact:** The Ollama tray watchdog (`ollama app.exe`, which auto-relaunches `ollama.exe serve` on kill) had to be stopped so a manually-launched server with the correct `OLLAMA_MODELS` env var would stick. `shared/utilities/llm_provider.py` is unaffected (it only needs `OLLAMA_HOST`, not the model storage path). Anyone resuming this project on this machine should launch Ollama's server manually with `OLLAMA_MODELS=D:\ollama_models` if the tray app was disabled, or re-enable the tray app after confirming it picks up the persisted env var on next login.

## D-009 — Reliability fixes for local-model structured output (discovery pipeline)
- **Date:** 2026-08-27
- **Decision:** Four fixes were required to get the Research Discovery Service running reliably end-to-end against `qwen3.5:9b`, all in `shared/utilities/llm_provider.py` and `services/research-discovery/discovery/`:
  1. **`think=False` on all three LLM calls** (query generation, full-text mining, gap/novelty analysis). The model runs a visible "thinking" reasoning mode by default, and reasoning tokens count against the same output budget as the actual JSON answer. Thinking unpredictably consumed the entire token budget before any schema JSON was produced — first on query generation (1000-token budget, empty result), then on full-text mining (12000-token budget, empty result, handled gracefully as best-effort), then on the main gap analysis (32000-token budget, empty result — NOT best-effort, aborted the run). Confirmed via direct Ollama API testing that `think:false` produces the same correct JSON in a fraction of the time and cost.
  2. **Explicit, tiered `num_ctx`** (`_context_window_for()` in `llm_provider.py`). Ollama's server-side default context window is far smaller than this model's 256K support and silently truncates generation once prompt+output exceed it — regardless of `num_predict`/`max_tokens`. A single large fixed context (tried at 24576) fixed the truncation but caused a different problem: on an 8GB GPU, a bigger context reserves proportionally more VRAM for KV cache, and this pushed inference into partial CPU offload (`31/34 layers to GPU`) even for small calls, making everything much slower. The fix scales `num_ctx` to each call's actual need (`_context_window_for`, tiered at 4096/8192/16384/24576/32768) so cheap calls stay cheap and only the calls that need headroom pay for it.
  3. **Trimmed `REPORT_SCHEMA` verbosity and reduced `max_tokens`** in `analysis.py` (themes 3-6→2-4, gaps 4-8→2-4; mining 12000→6000, gap analysis 32000→8000). A schema demanding 4-8 well-evidenced gaps is disproportionate for a 6-9 paper MVP corpus, and was driving unnecessarily long generations on this hardware.
  4. **`MAX_CANDIDATES_FOR_ANALYSIS = 5` cap** in `pipeline.py`. The gap-analysis schema requires one full JSON entry per author-flagged candidate with no cap of its own, so an uncapped mining result (observed: 10 candidates) scaled the final synthesis call's output size directly. Mining already orders candidates most-to-least substantive, so capping keeps the strongest ones.
  - A fifth, trivial bug (not a design decision, just a typo) was also fixed: `analyze_gaps()` read `comp.input_tokens`/`comp.output_tokens`, but `llm_provider.Completion` names those fields `prompt_tokens`/`completion_tokens`. This crashed the pipeline on the very last line, *after* a fully successful generation — first found when a run reached `n_tokens=8235, truncated=0` (proof the earlier fixes worked) and then crashed on this attribute access.
- **Reason:** Verified via multiple full end-to-end runs against the live model; see TILL_NOW.md for the successful run's stats.
- **Alternatives considered:** For (2), raising `max_tokens`/context indefinitely instead of tiering — rejected, this is what caused the CPU-offload slowdown in the first place. For (3)/(4), leaving the schema as-is and just waiting longer — rejected as impractical; a production run needs to complete in reasonable time on this hardware.
- **Impact:** `services/research-discovery/service.py::run_discovery()` now completes reliably end-to-end. This hardware (RTX 4060 8GB) is inherently slow for larger-context calls on a 9B model — later services should budget for this (keep schemas as compact as the task allows, cap any unbounded list before it reaches a synthesis prompt, and prefer `think=False` unless a specific step needs visible reasoning with a tested, generous token budget).

## D-007 — Research Discovery Service adaptation approach
- **Date:** 2026-08-26
- **Decision:** The Research Discovery Service's core pipeline (query generation → multi-source search → dedupe → rank → full-text mining → gap/novelty analysis) is retained as an async-generator pipeline emitting structured progress events — this already matches the project's required progress-event architecture. Adapted:
  - Swapped the cloud-provider LLM layer for `shared/utilities/llm_provider.py` (local Ollama only, no cloud fallback).
  - Removed personal-library integrations (a reference-manager sync feature and a citation-context enrichment feature) — out of scope for the MVP, added complexity/failure surface, and required data this system doesn't have.

  - Extended the gap-analysis output schema with explicit `novelty_analysis` (summary, supporting gaps, confidence, caveats) and `confidence_notes` fields, and extended query generation to also produce a `research_interpretation` field — both required by the project's output contract but not present in the original schema.
- **Reason:** Reuse-first per project rules; the four literature sources kept (Semantic Scholar, OpenAlex, PubMed, arXiv) all work with no API key, satisfying the "local AI + no external key" requirement for this stage.
- **Alternatives considered:** Running it as a separate HTTP microservice — rejected for MVP simplicity; can be revisited if a future web frontend needs direct access to this stage in isolation.
- **Impact:** `services/research-discovery/service.py::run_discovery()` is the stable entry point Service 2 and the orchestrator depend on; output conforms to `shared/contracts/discovery_contract.py::DiscoveryResult`.

## D-010 — Research Writing Service adaptation approach
- **Date:** 2026-08-27
- **Decision:** Adapted a LangGraph-based literature-review/writing agent as the Research Writing Service (`services/research-writing/`), reusing its outline-driven section-writing graph (`writing/graph.py`, `writing/modules/*`) and replacing only what didn't fit:
  - Its original two-agent design (search + write) is reduced to the writing agent only — Service 1 already covers search/discovery, so its own literature-search step is dropped entirely.
  - Its evidence-extraction step runs directly on Service 1's already-fetched abstracts rather than requiring the original design's manual PDF-download step. `services/research-writing/writing_prep.py` builds one Markdown "literature file" per selected paper (front matter + abstract, `evidence_depth: abstract`) and a heading outline (one root heading, gap titles as literature-review subsections) directly from a `DiscoveryResult` — no re-scraping.
  - Its LLM call layer was swappable as designed: `writing/adapters/ollama_model.py` implements the repo's `LanguageModel` protocol against `shared/utilities/llm_provider.py` (the same local-first provider from D-003), using Ollama's native schema-constrained decoding rather than the original prompt-engineered JSON-mode adapter (more reliable on a small local model — consistent with D-009's findings).
  - `shared/contracts/writing_contract.py` defines `WritingRequest`/`WritingResult` as the stage's input/output contract; `WritingRequest.target_format` is extensible (`IEEE`/`Springer`/`ACM`/`APA`/`Other` today, mapped to a citation style, with `format_other_name` for anything not yet listed) per the project's format requirement.
  - `services/research-writing/service.py::run_writing()` is the stable async-generator entry point (progress events + final `WritingResult`), matching Service 1's event-streaming shape.
  - Runs with `FAST_REVIEW_CONFIG` (all revision/audit rounds disabled, one retry each for section writing and card extraction) — this hardware is too slow for the graph's default multi-round revise/audit loop (each round re-runs every leaf section through the model).
  - `_context_window_for()` in `shared/utilities/llm_provider.py` (D-009) was extended to take the actual prompt length (`prompt_chars`) rather than sizing purely off `max_tokens` — the writing graph's per-section prompts (full literature files, not just a short query) are large enough that sizing from output length alone under-allocated context and caused slow mid-generation context-window shifts. Discovery's `Paper`/`PaperMetadata` now also carry the raw `abstract` field through to the contract (previously only a `has_abstract` boolean was exposed), since the writing service's literature files need the actual text.
- **Reason:** Reuse-first per project rules (see the "Do Not Rebuild Existing Work" working rule); the graph's outline-driven, evidence-file-based writing approach already matches this project's "evidence-grounded draft, structured contracts, no loose text between services" requirement.
- **Alternatives considered:** Keeping the original two-agent search+write pipeline and running Service 1's output through it as if it were freshly discovered — rejected, redundant work and loses Service 1's gap/novelty analysis. Full-text PDF ingestion instead of abstract-only literature files — deferred; Service 1 doesn't reliably produce full text for every paper, and abstract-depth evidence is sufficient to validate the pipeline wiring end-to-end (a full-text upgrade is a Service 1 enhancement, not a Service 2 blocker).
- **Known limitation:** On this hardware, leaf-section writing reliability (one LLM call per outline leaf, run at `max_concurrency=2`) is the main remaining source of partial/empty sections in a full-size outline — mitigated by capping retries (not eliminating the failure) and reported via `WritingResult.draft_metadata.warnings`/`errors` rather than hidden. A faster model/machine would allow re-enabling revision/audit rounds and higher concurrency.
- **Verification:** Unit tests (`tests/services/test_writing_prep.py`) cover outline/literature-file generation in isolation. `tests/services/test_writing_pipeline_integration.py` runs the full service against the live local model with a minimal two-paper/four-section case and checks for real cited, evidence-grounded output (skips cleanly if Ollama isn't reachable). `scripts/smoke_test_writing.py` is a manual end-to-end runner for the same minimal case. A production-sized outline was not run end-to-end during development — each leaf section is a separate LLM call, so a full run is expected to take a long time on this hardware (see the FAST_REVIEW_CONFIG note above); this is tracked as a follow-up before Review 2, not a blocker for Service 2 working "in isolation."
- **Impact:** `services/research-writing/service.py::run_writing()` is the stable entry point Service 3 depends on; output conforms to `shared/contracts/writing_contract.py::WritingResult`.

## D-011 — Fixed near-total section failure in Service 2's first full-corpus run
- **Date:** 2026-08-27
- **Decision:** Removed per-research-gap literature-review subsections from `writing_prep.py::build_outline()` and instead render Discovery's research gaps and novelty analysis directly as Markdown (`render_research_gap_section()`), spliced into the assembled draft by `service.py` rather than routed through the writing graph's evidence-gated leaf writer.
- **Reason:** A real end-to-end timing run (6 papers, 5 Discovery-identified gaps, ~15.4 minutes total: 245s discovery + 681s writing) produced only 2 of 13 outline sections successfully — all 5 per-gap subsections plus Research Gap, Proposed Novelty, Methodology, and Discussion failed with "insufficient evidence." Root cause, confirmed by inspecting the run's `tag_definitions.json`/`tag_coverage.json`/`literature_cards/*.json`: each Discovery gap is already a narrow, specific statement (e.g. "Absence of Direct Measures of Neuronal Metabolism... in Diabetic Models") derived from ~1 paper. Turning each into its own literature-review subsection made the writing graph's own tag-semantics step (`define_tag_semantics.md`) generate matching narrow `include_when`/`exclude_when` criteria, which then (correctly, per that step's own "never fill a tag by inference" rule) excluded almost the entire rest of the corpus — even a paper squarely on-topic (Anton et al., on IF's metabolic mechanisms) got zero points assigned to *any* tag, including the root/general one, because none of its content matched any gap's narrow criteria. This is the writing graph behaving exactly as designed for a genuine multi-paper thematic review outline; the bug was in how Service 2's outline builder used it.
- **Alternatives considered:** Loosening the tag-semantics prompt to be less strict — rejected, this is the underlying tool's core evidence-integrity guarantee and the project explicitly requires "not silently inventing" unsupported content. Keeping per-gap subsections but feeding full-text instead of abstracts — deferred; wouldn't fix the structural mismatch (a gap statement about one specific missing measurement isn't a topic multiple papers can speak to, regardless of evidence depth). The fix instead treats Discovery's gap/novelty analysis for what it already is: Service 1's own finished synthesis, not raw literature requiring re-evidencing by Service 2.
- **Impact:** `services/research-writing/writing_prep.py::build_outline()` now produces a flat Introduction / Literature Review / Limitations / Conclusion outline; `render_research_gap_section()` and its splice point in `service.py::run_writing()` are new. A related, separate issue was also observed and left unfixed: one of Service 1's 6 selected papers for the first run was an unrelated asthma-management guideline, a Discovery-side relevance/ranking bug worth investigating before Review 2, not a Service 2 defect.
- **Re-verification (same day, second full run, fresh 6-paper corpus):** The guaranteed-failure structural bug is confirmed fixed — no run-wide "insufficient evidence" wipeout. However, still only 2 of 4 leaf sections succeeded, this time for a different, more ordinary reason: `qwen3.5:9b` twice assigned the same evidence point to both a tag and its own ancestor (e.g. `TAG-ROOT` and `TAG-2`), which `build_literature_card.md`'s "assign only to the deepest matching tag" rule and the graph's own validation correctly reject — the affected paper's card failed after its retry budget (`max_card_attempts=2`), starving the Literature Review section of evidence and cascading into an empty-content validation error. This is model instruction-following reliability, not an outline-design defect, and is the same category of hardware/model limitation D-010 already flagged ("leaf-section writing reliability... is the main remaining source of partial/empty sections... mitigated by capping retries, not eliminated"). Not fixing further for now — the cost/benefit of chasing every small-model tagging mistake is poor on this hardware (each attempt is itself a ~15-minute run), and Service 2's contract already surfaces such failures honestly via `warnings`/`errors` rather than silently producing ungrounded content. Revisit if a faster model/machine becomes available (D-010's suggestion to re-enable revision/audit rounds and raise `max_card_attempts` would likely help).

## D-012 — Citation Verification Service adaptation approach
- **Date:** 2026-08-27
- **Decision:** Adapted the DOI/URL-verification piece of a full-stack literature-review web app as the Citation Verification Service (`services/verification/`) — not the whole source app, which is a paid-API-heavy (Scopus, Zotero, SerpAPI, OpenRouter), full-stack (FastAPI + Next.js) research tool built around a different end-to-end workflow than this project's pipeline.
  - Reused only its narrow, genuinely reusable core idea: parse a DOI out of each rendered reference-list entry and check it against a scholarly API, never inventing or silently repairing an unresolvable one. The source app's own DOI check uses paid Scopus with a Crossref fallback; this project has no Scopus key, so Service 3 uses Crossref as primary and OpenAlex as a fallback (both free/keyless — same "no external key" pattern as Service 1, D-007, and OpenAlex is already a dependency this project trusts).
  - `shared/contracts/verification_contract.py` defines `VerificationRequest`/`VerificationResult` as the stage's input/output contract, taking Service 2's `WritingResult` directly (no re-parsing of raw draft text needed — `WritingResult.reference_candidates` already gives one formatted, DOI-bearing string per reference).
  - `services/verification/service.py::run_verification()` is the async-generator entry point (progress events + final `VerificationResult`), matching Services 1–2's event-streaming shape. `extract_doi()` handles both DOI-suffix styles Service 2's citation formatter produces (`doi: 10.x/y` for IEEE/Vancouver, `https://doi.org/10.x/y` for author-year/MLA styles).
  - Three outcomes per reference, never collapsed into a binary pass/fail: `verified` (DOI resolved), `invalid` (a DOI was found but resolves nowhere — flagged as possibly incorrect or fabricated), `unverifiable` (no DOI present to check at all — flagged, not treated as a failure). A basic `missing_references` check compares `draft_metadata.papers_cited` against the reference-list count as a coarse citation-completeness signal.
  - Deliberately does NOT attempt the source app's "re-search for a replacement paper" step for a failed DOI (see its `api/workflow.py` re-search-agent pattern) — out of scope for this MVP; flagging honestly satisfies the "must not silently invent or repair" requirement without adding a second corpus-search dependency. Also deliberately does NOT attempt positional in-text citation-marker verification (matching every `[1]`/`(Author, Year)` occurrence in the draft body back to a reference) — the reference-list-level check (verified/invalid/unverifiable counts plus the cited-vs-listed count check) is the higher-value, lower-complexity check for now; full positional verification is a documented future enhancement, not a blocker.
- **Reason:** Reuse-first per project rules; a full paid-API research app would have been a poor fit to adapt wholesale, but its DOI-verification pattern (grounding citations against a real external source rather than trusting LLM output) is exactly this project's Service 3 requirement, and translates cleanly to a keyless equivalent.
- **Alternatives considered:** Adapting the source app's full retrieval+synthesis+Zotero pipeline — rejected, redundant with Services 1–2 and dependent on paid keys this project doesn't use. Requiring a Scopus key to match the source app's primary check — rejected, breaks the project's local-first/no-external-key requirement for a service this early in the pipeline. Attempting automatic reference repair via re-search — deferred, not required by the MVP spec ("flag it... otherwise keep it as a validation issue" already satisfies the requirement).
- **Verification:** Unit tests (`tests/services/test_verification_service.py`) cover DOI extraction across citation styles and the verified/invalid/unverifiable/missing-references classification logic using a mocked HTTP transport (no network needed). An integration test (`tests/services/test_verification_pipeline_integration.py`) and `scripts/smoke_test_verification.py` both run against the live Crossref/OpenAlex APIs with one real DOI, one fabricated DOI, and one DOI-less reference, confirming all three outcome branches — verified live end-to-end.
- **Impact:** `services/verification/service.py::run_verification()` is the stable entry point Service 4 depends on; output conforms to `shared/contracts/verification_contract.py::VerificationResult`.

## D-013 — Quality Assurance Service adaptation approach
- **Date:** 2026-08-27
- **Decision:** Adapted the deterministic (non-API) citation-audit and evaluation-reflection logic of a larger multi-agent literature-review system as the Quality Assurance Service (`services/quality-assurance/`) — not that system's own discovery/writing/persistence/workbench infrastructure, which duplicates Services 1–3 and is built around a different corpus format.
  - Reused the core idea of its citation auditor: scan the draft for high-risk factual/empirical sentences (numbers, "shows/reports/demonstrates/improves" etc.) with no citation at all (`find_missing_citations`), and separately flag *cited* sentences whose wording doesn't token-overlap enough with the paper(s) they cite (`find_unsupported_claims`) — a lightweight, fully deterministic claim-to-evidence alignment check requiring no extra model call.
  - Adapted, not copied: the source system's citation pattern (`[LetterKey]`) doesn't match this project's numeric `[1]`/`[2]` IEEE-style citations, so `services/quality-assurance/service.py` uses its own `\[(\d+)\]` pattern. Its claim-support check compares against an in-repo `data/papers.json` corpus's title/category/contribution/tags; this project instead matches each numbered reference back to its original `DiscoveryResult` paper **by DOI** (`build_reference_profiles`) and compares against that paper's real title/abstract text — richer and already-verified (via Service 3) rather than a curated in-repo fixture.
  - Deliberately treats an unmatched DOI (no Discovery record found) as a **known limitation**, not a false "unsupported claim" — the source system's design assumes every citation key always resolves to a full corpus profile, which doesn't hold here (Service 3 can verify a DOI exists without Service 4 being able to trace it back to the exact Discovery record, e.g. if metadata normalization differs slightly).
  - `shared/contracts/qa_contract.py` defines `QualityAssuranceRequest`/`QualityAssuranceResult`. Unlike Services 1–3, the request bundles all three prior stages' outputs (`DiscoveryResult`, `WritingResult`, `VerificationResult`) — an independent final audit needs the original evidence, the draft, and the citation checks together, not just the immediately preceding stage's output.
  - `services/quality-assurance/service.py::run_quality_assurance()` is the async-generator entry point, matching Services 1–3's event-streaming shape, even though the work itself is synchronous — kept for pipeline consistency (the orchestrator can treat all four stages uniformly).
  - **Deliberately does not call the local LLM at all.** Grading a draft with the same model that wrote it (`qwen3.5:9b`) is a weaker independence guarantee than deterministic, rule-based checks, and this hardware is already the bottleneck for Services 1–2 (D-009/D-010) — a QA pass that adds more slow model calls would undercut its own point as a fast, final, trustworthy gate. Scores (`citation_integrity`, `claim_source_alignment`, `process_control`, `literature_coverage`, `overall`, each 0–5) are computed from Service 3's verified/invalid/unverifiable counts, Service 4's own missing-citation/unsupported-claim/missing-section findings, and Service 2's own reported warnings/errors — mirroring the source system's non-API deterministic scoring path, not its optional API-backed one.
  - Also adapted, not reused: the source system's `FinalVerificationReviewer` (checks that a separate "polish" pass didn't silently change citations/headings/references). This project's pipeline has no separate polish stage between Writing and Verification, so that check doesn't apply — out of scope, not overlooked.
- **Reason:** Reuse-first per project rules; the source system's citation-integrity and claim-alignment heuristics are genuinely reusable ideas independent of its specific corpus format or API mode, and a deterministic final gate is both faster and more trustworthy than another LLM pass on this hardware.
- **Alternatives considered:** Running the source system's full multi-agent review/revision loop (writer ↔ reviewer ↔ polish iterations) — rejected, duplicates Service 2's own writing loop and this project's Services 1–3 already produce the evidence/citation checks that loop exists to enforce. Using the local LLM for an "independent" review pass — rejected per the self-grading concern above; revisit only if a second, materially different model becomes available on this hardware. Requiring every reference to resolve to a matched Discovery record — rejected, too strict given Service 3 verifies DOIs independently of Service 4's own DOI-to-record matching.
- **Verification:** Unit tests (`tests/services/test_qa_service.py`) cover missing-citation detection, DOI-based profile matching, unsupported-claim detection (including the "don't flag an unmatched DOI" case), missing-section detection, and a full `run_quality_assurance()` pass — all fast and network-free (no LLM, no HTTP). `scripts/smoke_test_full_pipeline.py` now chains all four services end-to-end against real Discovery/Writing/Verification output for a live check.
- **Impact:** `services/quality-assurance/service.py::run_quality_assurance()` is the pipeline's final stage; its `QualityAssuranceResult` is the terminal artifact PROJECT_NOTES.md's "Final Research Paper Draft" output describes.

## D-014 — Orchestrator and terminal app
- **Date:** 2026-08-27
- **Decision:** Built `orchestrator/pipeline.py::run_pipeline()` as a pure-Python async-generator pipeline runner (no HTTP layer yet) that takes one `ResearchRequest` (`shared/contracts/pipeline_contract.py`) and runs Services 1→2→3→4 in sequence, persisting each stage's structured result under `outputs/<topic-slug>_<run-id>/NN_<stage>/result.json` plus a `final/` folder (draft, quality report, validation report, reference list) and a top-level `metadata.json`. `terminal_app/cli.py` is the current user-facing interface described in PROJECT_NOTES.md — it collects the request (interactively, or from a single command-line argument for quick runs), calls the orchestrator, and prints each progress event plus a final summary.

This is the explicit "create adapters when formats don't match" rule applied to progress events, not just data contracts.
  - Each of the four services' entry points is a bare `service.py` reached only via `sys.path` insertion (the recurring naming collision first hit in D-010, worked around per-test-file since). The orchestrator is the first place all four get imported into one process, so it loads each one by explicit file path under a unique module name (`_load_service()`) up front, rather than adding a fifth ad hoc workaround.

- **Alternatives considered:** Writing the FastAPI endpoint first and driving the terminal app through HTTP — rejected for now; an in-process call is simpler and sufficient until a real second consumer (a web frontend) needs the HTTP boundary, and PROJECT_NOTES.md itself frames the terminal app as "the current interface," not the API.
- **Verification:** `tests/orchestrator/test_pipeline.py` fakes all four services (fast, no network/LLM calls) and checks artifact persistence, standardized progress-event shape, and that a stage producing no result raises `PipelineError` rather than silently continuing. `scripts/smoke_test_full_pipeline.py` now calls `run_pipeline()` directly (previously it manually chained the four services) and was re-run live end-to-end successfully.
- **Impact:** `orchestrator/pipeline.py::run_pipeline()` is the stable entry point for both the terminal app and any future API layer. Remaining for Review 3: the `POST /research` backend API, and progress/event streaming over that API (explicitly deferred per the project's own sequencing rule).

## D-017 — Asynchronous run API: POST /research/runs, GET /research/runs/{run_id}, SSE events
- **Date:** 2026-08-27
- **Decision:** Added an asynchronous path alongside the existing synchronous `POST /research` (D-015), which is left unchanged for backward compatibility:
  - `POST /research/runs` starts a pipeline run as a background `asyncio` task and returns `{run_id}` immediately (202 Accepted), instead of blocking for the run's full duration.
  - `GET /research/runs/{run_id}` returns the run's current status (`running`/`completed`/`failed`), its `PipelineResult` once completed, or its error message if failed. Returns 404 for an unknown run_id.
  - `GET /research/runs/{run_id}/events` streams every progress event as Server-Sent Events (`text/event-stream`), including events that happened before the client connected (a late subscriber still sees full history, not just what happens from then on), ending with an `event: end` marker. Returns 404 for an unknown run_id.
  - `orchestrator/run_registry.py` is new: an in-memory `dict[run_id, RunState]` with a small pub/sub fan-out (one `asyncio.Queue` per subscriber) so multiple SSE clients could watch the same run simultaneously, though only one is expected in practice for this MVP.
  - `orchestrator/pipeline.py::run_pipeline()` gained an optional `run_id` parameter (defaulting to generating one internally, as before) so the API can generate the run_id up front and return it to the client before the pipeline itself has emitted its first event.
- **Reason:** The project brief explicitly named `GET /research/{run_id}` and progress/event streaming as later additions, deferred at D-015 specifically until the synchronous path was proven — which it now is (D-015's live verification, plus every service chained live through D-016's full-pipeline test). A run can take 15+ minutes on this hardware, so a caller that wants to show live progress (the terminal app already does this in-process; a future web frontend would need it over HTTP) needs a non-blocking start + poll/stream pattern rather than one long-held connection.
- **Alternatives considered:** Replacing `POST /research` outright with the async version — rejected; the synchronous endpoint is already tested and used, and breaking it would be scope creep beyond "add streaming" into "redesign the API." A persistent job queue/database (Celery, Redis, etc.) instead of an in-memory registry — rejected as over-engineering for a single-process local MVP with no multi-worker deployment; the in-memory registry is lost on restart, same limitation the synchronous endpoint already has (a run's live state was never persisted anywhere but the calling process either way — only the on-disk artifacts under `outputs/` survive a restart, for both endpoints equally).
- **Verification:** Unit tests (`tests/orchestrator/test_api.py`) cover: run_id returned immediately, polling to `completed` with the correct result, polling to `failed` with the error message on `PipelineError`, 404 for both GET endpoints on an unknown run_id, and the SSE stream containing the expected progress/result payloads followed by the end marker — all fast, pipeline faked out. Also manually verified against a real running `uvicorn` server: `POST /research/runs` against a real request returned a run_id immediately, `GET /research/runs/{run_id}` showed `status: "running"`, and the SSE endpoint streamed real live progress events from an actual in-progress Discovery stage.
- **Bug found and fixed during this manual verification:** the Research Discovery Service's own progress-event text included a leftover string from its original source repo — `"Generating search queries with Claude…"` — inaccurate for this project, which only ever calls the local Ollama model (`qwen3.5:9b`), never Claude or any cloud model. This had been emitting silently all along (the terminal app already prints every event's `message` field) but was only actually read closely once the SSE stream's raw payload was inspected here. Fixed to `"Generating search queries with the local model…"`; two similar leftover code comments (one referencing "Claude", one referencing an unused "scite" integration from the source repo) were also cleaned up in the same file. This is a plain accuracy bug fix, unrelated to D-004's documentation-privacy rule — D-004 governs what project-facing *docs* say about component provenance, not runtime-user-facing text describing which model is actually running.
- **Impact:** `orchestrator/api.py` now exposes both the original synchronous endpoint and the new asynchronous/streaming trio; `orchestrator/run_registry.py` is the new supporting module. This completes the two explicitly-deferred API items from the project brief — no further API work is planned for this MVP.

## D-020 — Service 2 final reliability pass: tag-semantics overlap, the container-content bug, and revision rounds
- **Date:** 2026-08-28
- **Scope:** A dedicated follow-up to D-019, focused entirely on Service 2 (per explicit instruction: no new features, Service 1 untouched). Investigated and fixed the two concrete problems D-019 left open, plus one additional high-leverage finding made while stress-testing the fixes.

### Problem 1 — systematic TAG-ROOT/child overlap
- **Root cause (confirmed, not guessed):** `define_tag_semantics.md` instructed the model to "minimize overlap between branches" but only ever discussed *sibling* separation — it never told a parent/root tag to exclude what its own children already own. In the real P003 failure (D-019), `TAG-ROOT`'s generated `include_when` was "Evidence addresses both the intervention (intermittent fasting) and the outcome (cognitive performance)" — functionally identical in scope to the whole research question, so it legitimately overlapped every child's criteria too.
- **Fix:** `define_tag_semantics.md` gained an explicit "Ancestor/descendant ownership" section: any tag with children must write `include_when` to cover ONLY synthesis/cross-cutting content a child doesn't already own, and must add an `exclude_when` entry per child naming that child's scope as excluded. Leaf tags must symmetrically acknowledge the ancestor's synthesis role.
- **Verification (real model, targeted reproduction — not a full 15-minute pipeline run):** `scripts/repro_tag_overlap.py` reused the exact literature files and tag tree from the real run whose P003 card failed twice (D-019), and regenerated ONLY the tag semantics + P003's card with the fixed prompt (2 LLM calls, not a full pipeline). Result: `TAG-ROOT`'s new `include_when` narrowed to genuine overview-only content, its `exclude_when` explicitly named all four children, and **P003's card passed validation with zero ancestor/descendant duplication** — the exact real-world failure resolved.
- **New tests** (`tests/services/test_writing_card_tag_ownership.py`, 5 tests, no model needed): directly exercise `validate_literature_card()`'s existing ancestor/descendant detector against hand-built cards — root-only evidence (valid), child-owned evidence (valid, root need not duplicate), ancestor/descendant conflict at two different depths (rejected), and sibling sharing (explicitly permitted, not flagged — matching the documented "a genuinely cross-branch claim may reuse one point ID" design).

### Problem 2 — the outer "blind retry" / empty-content crash
- **Actual root cause, found by tracing the exact control flow (not assumed):** `writing/graph.py::write_next_section`'s **container-tag branch** directly constructed `SectionDraft(tag_id=tag_id, content="", ...)` — violating `SectionDraft.content`'s own `Field(min_length=1)`. This is a **deterministic code bug**, not a model-reliability issue: it crashes on *every* run where any outline tag is classified `node_type: "container"`, regardless of what the model returns. This explains why the "blind retry" symptom was unfixable by retrying — the identical invalid string is constructed by code on every attempt, independent of the model entirely.
- **Fix:** the container branch now passes `content=" "` (a single space) instead of `""` — satisfies the schema's `min_length=1` while still rendering as empty, since `review_assembler.py::assemble_review()` already checks `draft.content.strip()` before emitting any body text for a section (a container was always meant to contribute only its heading).
- **Reproduction discipline followed:** `tests/services/test_writing_container_section_bug.py` was written and run to reproduce the *exact* production error message (verbatim, including the pydantic `string_too_short` text) **before** the fix was applied, confirming the diagnosis; then re-run after the fix to confirm resolution (2/2 tests, no live model needed — the bug is 100% reproducible without any LLM call).
- **Scoping decision — no "failure classification system" or "recovery-prompt" mechanism was built for this pass.** Investigating this bug revealed it was never actually a model-output problem, so the elaborate retry-classification framework in the pass's own instructions turned out not to be the right lever for the one concrete, reproduced failure. Building it anyway for a hypothetical case with no supporting evidence would be exactly the "large speculative rewrite" this pass's own rules warn against. Instead: `tests/services/test_writing_outer_retry_bounded.py` (4 tests) verifies the *existing* outer-retry behavior is safe for a genuinely-empty model response (bounded attempts, no infinite loop, the exact validation error is captured in `ReviewResult.errors` rather than swallowed, explicit failure state) — and `tests/services/test_writing_section_isolation.py` confirms one section's failure never blocks or corrupts independent sections. This is honestly documented as verified-safe-but-still-blind for that hypothetical case, not silently left untested.

### Additional finding made while stress-testing the above two fixes: revision rounds were effectively disabled

## D-021 — Service 2 final citation-boundary fix: false-positive "invalid citation" detection
- **Date:** 2026-08-28
- **Scope:** A dedicated follow-up to D-020, focused entirely on Service 2's one remaining stress-test failure — a section reported as citing "papers outside its allowed evidence set." Per explicit instruction, the root cause was traced through the real failed run's saved artifacts before any code was changed, and the assumption in the task brief ("the model cited a forbidden paper") was checked against evidence rather than taken at face value.

### 🔍 Root cause — NOT what was assumed
Tracing the exact real run (`section_contexts/TAG-2.json`, `section_audits/TAG-2.json` from the remote-work stress run in D-020) showed the model cited **only allowed papers** (P001, P003, P004, P005 — all in `allowed_paper_ids`). There was no genuine evidence-boundary violation. The audit's own `invalid_paper_ids` were `["@P001", "@P003", "@P004", "@P005"]` — with a literal `"@"` prefix that does not exist in `allowed_paper_ids` (bare IDs). The model had copied the `@`-decorated form of its own `[@P001]` prose placeholder into the separate `cited_paper_ids` structured-output field, where only the bare ID (`"P001"`) belongs. Every downstream comparison (`draft.cited_paper_ids` vs `allowed_paper_ids`; `draft.cited_paper_ids` vs the placeholder IDs extracted from prose) is a set-equality check, so this single formatting slip made every citation in the section look simultaneously "outside the allowed list" and "not matching the prose placeholders" — even though the underlying evidence use was entirely correct. This is a **false-positive detection bug**, not the evidence-boundary leak the task brief assumed; reported here exactly as traced, not as assumed.
- A second, mirror-image variant was found while stress-testing the fix on a fresh run of the *same* fasting/cognition topic: a different section (`TAG-1`) had correctly bare `cited_paper_ids` (`["P002", "P001"]`) but wrote prose placeholders **missing** the `@` (`[P002]` instead of `[@P002]`), so `extract_cited_paper_ids()` found zero placeholders and flagged the same "doesn't match" symptom in the opposite direction. Same underlying confusion (the model does not reliably keep the two citation representations — prose placeholder vs. structured field — distinct), manifesting both ways.

### 🛠️ Fix — smallest correct modification at the schema/extraction boundary, not a new architecture
1. **`writing/schemas.py`**: `SectionDraft` and `SectionDraftContent` (which `ReviewRevisionContent.sections` also uses) gained a `field_validator` on `cited_paper_ids` that strips a stray leading `@` and/or wrapping `[]` from each entry before storage. This guarantees every `cited_paper_ids` value is normalized at construction time regardless of which call site produced it (initial write, revision, introduction/conclusion, full-review revision) — a single fix point rather than patching each of the 5+ call sites individually.
2. **`writing/modules/citation_formatter.py`**: `_CITATION`'s regex changed from `\[@(?P<paper_id>P\d{3,})\]` to `\[@?(?P<paper_id>P\d{3,})\]` — the `@` is now optional when extracting (and rendering) prose placeholders, so a bare `[P001]` slip still resolves to the same citation instead of vanishing from extraction entirely. `P\d{3,}` is paper-ID-specific, so this does not risk matching unrelated bracketed text.
3. **`writing/prompts/editorial_standard.md`** (prepended to every generation/revision/audit prompt): added one explicit line stating `cited_paper_ids` values must be the bare ID only, never the `@`-decorated placeholder form — reduces recurrence at the source, though the schema-level normalization now makes the mistake harmless even when it still happens.
4. **`writing/prompts/revise_section.md`**: added an explicit instruction for the case where a citation genuinely is out of scope — check whether an allowed paper's own points actually support the claim before citing it; if none do, remove or rewrite the claim rather than attaching an allowed paper's citation to a claim its evidence doesn't support. Satisfies the explicit "never fabricate a false citation to raise completeness" requirement, in case a genuine (not merely formatting-based) violation occurs.
- **Why this is the smallest correct fix, not a "clearer evidence boundary" architecture change:** the task brief suggested restructuring the evidence context into an explicit "SECTION EVIDENCE SET" block. Tracing the actual failure showed the evidence boundary itself (`allowed_paper_ids`, `direct_points`, `SectionWritingContext`) was never the problem — the model already respected it correctly. Rebuilding the context format to solve a bug that was actually a citation-ID string-formatting mismatch would have been the "large speculative rewrite" this pass's own rules warn against; normalizing the two representations that are already correct in substance is the change the evidence actually supports.

## D-023 — Security fix: Gemini API key leaked via query-parameter URL in error output
- **Date:** 2026-08-28
- **Severity:** Real secret exposure, found during live testing with a real user-supplied API key.
- **What happened:** During the first live test of the Gemini provider (D-022) with a real key, the Gemini API returned a transient `503`. `_stream_json_gemini()` sent the key as a URL query parameter (`?key=...`, per Google's own REST API convention) and caught the resulting `httpx.HTTPStatusError` to re-raise a clean, key-free `LLMProviderError` message — but did so with a bare `raise LLMProviderError(...)` inside the `except` block, which Python implicitly chains to the original exception. The original `httpx.HTTPStatusError`'s own string representation includes the full request URL, so the raw API key was printed in the traceback output despite the new exception's own message being clean. **The key was exposed in this session's tool output/transcript as a direct result.** The user was immediately advised to revoke/regenerate the key in Google AI Studio.
- **Root cause:** Two independent, compounding mistakes: (1) sending the key via URL query parameter at all, when Gemini's API also accepts it via an `x-goog-api-key` header; (2) not suppressing Python's automatic exception chaining, which surfaces the ORIGINAL exception's message (containing the leaked URL) even when the code being read only shows the new, clean exception being raised.
- **Fix:**
  1. `_stream_json_gemini()` now sends the key via the `x-goog-api-key` request header, never in the URL — the key can no longer appear in the request URL at all, regardless of what does or doesn't get logged.
  2. Every `raise LLMProviderError(...)` inside `_stream_json_gemini()`'s exception handlers now uses `raise ... from None`, suppressing the chained original exception from ever appearing in a printed traceback — defense in depth, so even an unrelated future exception carrying sensitive request detail can't leak the same way.
- **Verification:** Two new regression tests (`tests/shared/test_llm_provider.py`): one confirms the key is sent as a header and never appears in the request URL or `params`; the other reproduces the exact original bug (a fake `httpx.HTTPStatusError` whose message contains a secret-looking URL) and asserts the secret appears in **neither** the raised exception's message **nor its fully-printed traceback** — the real leak vector, not just the surface-level message.
- **Reason:** A live-testing incident, not a theoretical review finding — this is exactly the kind of bug real end-to-end testing (rather than unit tests alone) is meant to catch, and is reported here with full honesty per this project's own standing documentation practice.
- **Impact:** No secret from this incident lives in the repository, any commit, or any generated artifact — the key only ever existed in a local scratch file (outside the repo, deleted immediately after use) and this session's tool-output transcript, which is why revocation (not a code fix alone) was the correct immediate action. Confirms the wisdom of D-022's original design ("secrets... never printed, logged, or embedded" as a config-handling goal) — that goal was upheld for the *stored* key; this incident shows a *transmission-path* gap the original design didn't anticipate, now closed.

## D-030 — Quantified confirmation that raising Discovery's `max_tokens` ceiling is not the correct fix (real cost computed, not assumed)
- **Date:** 2026-08-29.
- **Scope:** a follow-up asked explicitly whether increasing the analysis output-limit ceiling (rather than only the D-029 prompt fix) would be safe, and whether the model/API even supports it — answered here with real, computed numbers rather than a qualitative judgment.
- **Finding:** `llm_provider.py::_context_window_for()` (this project's own local-model context-window tiering, deliberately sized for this 8GB-VRAM GPU per D-009) computes the actual Ollama context window from `max_tokens` and prompt size, using fixed tiers `4096/8192/16384/24576/32768`. The D-029 prompt-level fix already eliminated the observed failures at zero resource cost; raising the ceiling would impose a real, quantified 50%+ context-window cost on every call, with no demonstrated additional benefit. This is not an assumption — it is now a computed number.
- **Additional verification:** a third real Discovery+Writing run, on a genuinely new topic (not the previously-failing one), completed Discovery successfully and reached `draft_status: "complete"` — the third time in this project's real-run history. Combined with D-029's 2 same-topic reproductions: **3 of 3 real post-fix runs succeeded** (2 same-topic + 1 new-topic), versus 2 of 2 pre-fix failures on the originally-failing topic.

## D-031 — Trend & Gap Advisor added as an optional Stage 0, wired through its own CLI rather than into the existing pipeline
- **Date:** 2026-09-12.
- **Problem:** the pipeline (Discovery → Writing → Verification → QA) only starts once a student already has a research question. Choosing that question is the harder problem for most students, and there was no evidence-grounded way to answer "where is my field actually moving?" — see `docs/specs/trend-advisor-spec.md`.
- **Decision:** a new fifth service, `services/trend-advisor/service.py::run_trend_advisor()`, exposing the same async-generator progress-events-then-result shape as the existing four, plus a new `researchgenie-advise` console entry point (`researchgenie/advisor_cli.py`) registered in `pyproject.toml` alongside `researchgenie`.
- **How Stage 0 is wired into the orchestrator (user story 20), and the distinction that makes it safe:** the advisor is never *run* by `run_pipeline()`. It is interactive, and that function's entire contract is "yields events, never prompts" — putting a blocking chat loop inside it would break every existing caller, including the async `POST /research/runs` API endpoint. What is wired in is the advisor's **output**: `run_pipeline()` takes an optional `trend_advisor: TrendAdvisorResult | None`, and when a run was started from the advisor it persists that shortlist to `<run>/00_trend_advisor/result.json`, emits a Stage 0 progress event ahead of Discovery, records `chosen_topic`/`chosen_topic_gap_flagged` in `metadata.json`, and carries the result on `PipelineResult`.
- **Why output-wiring and not just letting the CLI run both:** the first cut had the advisor save to its own separate `outputs/<domain>_<run_id>/` folder while the pipeline saved to a different one, so a student who chained straight through got **two unrelated run folders** and the link between "why this topic" and "here is the paper" was lost. Stage 4's own requirement is that the orchestrator log every stage's input/output for audit; a run that began with a topic decision is not fully audited unless that decision is in the run. Found in code review against user story 20 — the spec's Implementation Decisions do say "`orchestrator/pipeline.py`'s existing four stages are untouched", and they still are: this is one optional parameter that is `None` on every existing code path, with a regression test asserting a plain run produces no Stage 0 event, no Stage 0 folder, and no new metadata key.
- **Net effect on existing behaviour:** zero changes to the four existing services' behaviour, contracts, or tests; the plain `researchgenie` entry point is unaffected; a plain run writes the same files, the same `metadata.json` keys, and emits the same events as before (asserted by a dedicated regression test). **One honest exception, recorded rather than glossed:** `PipelineResult` gains a nullable `trend_advisor` field, so the HTTP API's response body and its OpenAPI schema now carry `"trend_advisor": null` for every run, advisor-started or not. Additive and nullable, so no client breaks — but "byte-for-byte unchanged" is true of the disk output, not of the API contract.
- **Human confirmation is structural, not advisory:** the agent never commits a topic on the student's behalf. A pick is always the student's typed choice, parsed deterministically (`advisor_cli.parse_pick`), then re-confirmed, and the generated research question is shown for edit before anything downstream runs.
- **Only shared code touched:** `services/research-discovery/discovery/sources/openalex.py` gained two functions (`topic_counts`, `works_for_topic`) and a `_polite()` helper extracted from the existing `search()`. Extended rather than duplicated deliberately — a second OpenAlex client would not inherit this module's polite-pool handling, retry/backoff, or abstract reconstruction, each of which has already been a real bug once (D-028).
- **The pick is named, not positional (`TrendAdvisorResult.chosen_topic`).** The first version of the hand-off moved the student's choice to shortlist entry 0 and had the orchestrator read entry 0 back. Review found three separate faults in that one convention, all of which the named field removes at once: (1) the two modules were coupled only by a comment, so any reorder on either side would attribute the *wrong* topic to the student with no test failing; (2) the reorder matched the pick with `is not`, i.e. by object identity, so a candidate that had been through a JSON round-trip — as any saved-and-reloaded result has — was duplicated rather than moved (reproduced: a 3-topic shortlist came back with 4 entries); (3) re-sorting misrepresented what the student was actually shown, since the advisor deliberately ranks gap-flagged topics first. The shortlist is now passed through untouched as the context the decision was made against, and `chosen_topic` is `None` when a student stopped without picking (user story 10) — in which case no topic is attributed to them in the run metadata.
- **The pick also travels as a `ResearchRequest.keyword`,** since D-018 scores candidate papers against user keywords as its highest-confidence terms — so the chosen topic keeps steering Discovery even if the student rewrote the generated question into something looser.
- **The optional stage is opt-in in the TUI too.** The orchestrator emitted a Stage 0 event that `researchgenie/tui.py` silently dropped (its `_STAGE_ORDER` listed only the four real stages), so an advisor-started run showed no sign of the stage that produced its topic. `PipelineView(include_trend_advisor=True)` now prepends the row, and a plain run still shows exactly four stages rather than a row that would stay empty forever.
- **Tests:** 8 service-boundary tests (`tests/services/test_trend_advisor_service.py`) at the `run_trend_advisor()` level, matching `test_discovery_service.py`'s convention; 11 tests for the pick parser and the hand-off helper (`tests/researchgenie/test_advisor_pick_parsing.py`), including the identity-vs-value regression; 7 tests driving `main()` itself with the prompts faked (`tests/researchgenie/test_advisor_cli_handoff.py`) — added because review showed that *dropping either the `keywords` or the `trend_advisor` argument at the real call site left the whole suite green*, verified by mutating both and watching these fail; 6 orchestrator tests for optional Stage 0 (`tests/orchestrator/test_pipeline.py`), one proving a plain run is unchanged, one that the named pick is read rather than the first entry, one for a `chosen_topic` matching nothing; 5 TUI tests, including `render()` actually drawing (and omitting) the optional panel. The CLI's prompts/presentation get a manual smoke runner (`scripts/smoke_test_trend_advisor.py`) rather than a pytest suite, per the spec's agreed rigor split.
- **Impact:** the platform now covers "which topic?" as well as "write this topic up", with no risk surface added to the already-working pipeline. Test suite 190 → 254, all passing.

## D-032 — Publication velocity is computed arithmetically from live OpenAlex counts, never asked of the model
- **Date:** 2026-09-12.
- **Decision:** `trend_advisor/velocity.py` ranks topics by `recent_works / max(prior_works, 1)` over two three-year windows, using OpenAlex `group_by=primary_topic.id` counts. The model is never asked which topics are rising.
- **Why:** a model's answer to "what's hot in mechanical engineering" is unverifiable and drifts between runs — the exact opposite of what this stage is for. Every number a student sees here is one they can re-query themselves, which is what makes the shortlist recommendable by a professor (spec user stories 13, 16).
- **Hardcoded, verified domain → subfield table (`DOMAIN_SUBFIELDS`):** each of the six picklist domains maps to four OpenAlex subfield ids, every one of them read back from OpenAlex's own `/fields/{17,21,22}` subfield lists on 2026-09-12 rather than guessed or inferred at runtime. An LLM-generated mapping was rejected outright: it would make results irreproducible between runs for no benefit. Reproduced here in full so the mapping can be audited without reading `trend_advisor/velocity.py`:

| Domain | Subfield ids | Subfield names (OpenAlex) |
|---|---|---|
| `CS_AI_ML` | 1702, 1707, 1706, 1712 | Artificial Intelligence; Computer Vision & Pattern Recognition; Computer Science Applications; Software |
| `ECE` | 2208, 1705, 1711, 1708 | Electrical & Electronic Engineering; Computer Networks & Communications; Signal Processing; Hardware & Architecture |
| `EEE` | 2208, 2102, 2105, 2207 | Electrical & Electronic Engineering; Energy Engineering & Power Technology; Renewable Energy, Sustainability & the Environment; Control & Systems Engineering |
| `MECHANICAL` | 2210, 2211, 2202, 2209 | Mechanical Engineering; Mechanics of Materials; Aerospace Engineering; Industrial & Manufacturing Engineering |
| `CIVIL` | 2205, 2215, 2216, 2212 | Civil & Structural Engineering; Building & Construction; Architecture; Ocean Engineering |
| `CLOUD_DEVOPS` | 1710, 1712, 1705, 1708 | Information Systems; Software; Computer Networks & Communications; Hardware & Architecture |

  The two overlaps are deliberate, not duplication to be cleaned up: **2208** (Electrical & Electronic Engineering) sits in both ECE and EEE, and **1712** (Software) in both CS_AI_ML and CLOUD_DEVOPS, because those departments genuinely share that literature. Each domain lists the subfields a student in that department would recognize as theirs, so forcing disjoint sets would hand one of each pair a shortlist missing its own core venues. `Other` has no row — it falls back to a free-text OpenAlex search, which is why `TrendAdvisorRequest` requires `domain_other_name` for it.
- **Three non-obvious choices, each preventing a real failure:**
  - **The current year is excluded from both windows.** OpenAlex indexing lags, so a partial year always looks like a publication collapse — including 2026 would have inverted essentially every ranking. `windows()` compares the last three *complete* years against the three before them.
  - **`MIN_RECENT_WORKS = 200` floor.** Growth ratio alone is dominated by noise: three papers where there was one is a "3x rise" that means nothing and would have topped every shortlist. Topics below the floor are dropped before ranking.
  - **A topic absent from the prior window divides by 1, not by zero** — so a genuinely new topic ranks by its own recent volume rather than by an infinity.
- **Volume is kept alongside growth, not folded into it:** `paper_count` and the derived `is_crowded` flag (threshold 3000, chosen from the real OpenAlex distribution probed while building this — head topics run 30k-50k per subfield pair per window, the long tail runs in the hundreds) are what let a student choose between competing in a hot area and filling a quiet one (spec user story 5). A single blended score would have destroyed exactly that distinction.
- **Honest failure, not an empty list:** `VelocityUnavailable` is raised when OpenAlex is unreachable or a domain yields fewer than three rankable topics. A short or empty shortlist is never presented as a result.
- **arXiv is annotation only:** a secondary recent-preprint count, for CS-adjacent domains only (`ARXIV_DOMAINS`), reusing Discovery's existing arXiv connector. It returns `None` — never `0` — when arXiv fails, so an outage is never read as "no preprints exist". A real live run caught the inverse of this bug in the service layer: the arXiv-unreachable warning fired for MECHANICAL, a domain that never queries arXiv at all, reporting an outage that had not happened. It is now warned on only for domains that actually query it.
- **Tests:** 13 unit tests over mocked OpenAlex responses (`tests/services/test_trend_velocity.py`) covering the growth math, the volume floor, the divide-by-zero case, growth-beats-volume ranking, the crowded/quiet split, and both loud-failure paths; plus one live test against the real API (`test_trend_velocity_live.py`), skipped without network — it is the only thing that can catch a renamed filter or a retired subfield id, which no mock ever will.

## D-033 — Cross-paper gap mining runs as a LangGraph fan-out swarm, with a recurrence threshold and visible degradation
- **Date:** 2026-09-12.
- **Decision:** `trend_advisor/gap_mining.py` is a LangGraph `Send` fan-out — one worker per candidate paper, each extracting only the future-work/limitations statements actually present in that paper's own text — merged by an `operator.add`-reduced state field. Same Swarms pattern already proven in the Writing service's literature-card fan-out.
- **Why this signal exists at all:** publication volume says where people are already working; a recurring future-work mention says where they have publicly admitted they have *not*. A topic with the second and not the first is exactly the under-explored gap a student is looking for, and no amount of volume analysis can surface it.
- **`MIN_PAPERS_FLAGGING_A_GAP = 2`, counted in papers, not statements:** one paper's future-work sentence is that paper's opinion. The flag is set only when several independent papers contributed, which is what the word "recurring" is claiming. Evidence from a single paper is still attached and shown — it is evidence, just not a signal. **Bug found in review and fixed:** the first implementation keyed the contributor set on statement *text*, and the extraction prompt allows a paper up to 3 statements — so one paper returning two future-work sentences set "flagged by multiple independent papers" entirely on its own. `_MinedGap` now carries the paper's identity and the count is over distinct papers. Two regression tests pin both directions: one paper with several statements is not recurrence, and two papers with identical wording still is (so the fix cannot be re-broken by de-duplicating statement text).
- **`MAX_PAPERS_PER_TOPIC = 2`:** each worker is one local-model call, and on this hardware those are the whole stage's cost (D-009). Bounded per topic in the same spirit as Discovery's `MAX_CANDIDATES_FOR_ANALYSIS` cap, rather than fanning out over every example paper the velocity step found.
- **Workers read the paper's Discussion/Limitations/Future-research sections, not its abstract.** Authors state what is still unsolved in those sections; abstracts rarely carry them, so mining abstracts alone would have weakened the one signal this stage exists to provide (spec user story 4 says "future-work sections" explicitly). `velocity.py::_attach_future_work_text()` retrieves them by reusing Discovery's existing `fulltext` module (Europe PMC JATS, then an open-access PDF) — already tested, already bounded, and it never raises. Only the papers the swarm will actually read are fetched (`GAP_TEXT_PAPERS_PER_TOPIC`, matching the swarm's own cap); a paper with no reachable open-access copy falls back to its abstract, and a paper with neither is dropped rather than sent to the model to fabricate over. **Measured, not assumed:** on a real live CIVIL run, 2 of the 16 mining-eligible papers yielded retrievable future-work text (the rest are not open-access) — so the abstract fallback still carries most of the load, and the section text is an upgrade where it exists rather than a replacement. Raising that hit rate would mean paid/closed-access retrieval, which is out of scope; it is recorded here rather than left as an unexamined assumption. The prompt likewise names the empty list as the correct, expected answer for many papers.
- **Worker isolation:** one failed call costs that paper's findings and nothing else, matching the Writing swarm's rule. The recurrence threshold then treats the reduced evidence honestly on its own.
- **Model-provider outage is health-checked *before* the swarm, not inferred from failed workers.** Found while running the live smoke test with Ollama down: every worker failed, every topic came back with no gap evidence, and the output read "no recurring gaps found" — a finding, when the truth was "never checked". The service now checks `llm_provider.health_check()` first and, when the provider is down, emits a failed-stage event and a result warning stating explicitly that absent gap flags mean *not checked*, while still delivering the velocity half of the stage.
- **Tests:** 13 tests (`tests/services/test_trend_gap_mining.py`) running the real graph against a fake `LanguageModel` — no Ollama needed — matching `test_writing_literature_card_retry.py`'s pattern: the recurrence threshold in both directions plus the statements-vs-papers regression, no-fabrication on silent papers, per-topic evidence isolation across concurrent workers, worker-failure isolation, the per-topic cap, full-text-preferred-over-abstract in both directions, and text-less papers never reaching the model. Plus one service-level test that the provider outage is reported rather than read as a finding.

## D-034 — The orchestrator can run Stage 0, but never picks the topic
- **Date:** 2026-09-13.
- **Decision:** `orchestrator/pipeline.py` gains two entry points. `run_trend_advisor_stage()` runs Stage 0 alone, piping the advisor service's own events through the existing `_adapt_inner_event` so they arrive in the same shape as the four established stages. `run_advisor_then_pipeline()` runs Stage 0 and then `run_pipeline()` under the same `run_id`, with the chosen topic carried through as `ResearchRequest.research_question`. `run_pipeline()` itself is untouched, and a run that never invokes Stage 0 behaves exactly as before.
- **Why the orchestrator does not choose:** `run_advisor_then_pipeline()` takes a `select_topic(TrendAdvisorResult) -> str | None` callback rather than taking the top-ranked entry or asking a model. Picking the research topic is the one decision in this stage that belongs to the student (spec user story 10 — stopping to think it over is a supported outcome, not a failure), and an orchestrator that silently defaulted to `shortlist[0]` would quietly convert a ranking into a commitment. Returning `None` emits one `done` event and starts no pipeline. This keeps the orchestrator's contract identical to the CLI's existing `with_chosen_topic` hand-off, and means the orchestrator never depends on shortlist *position* — which matters because D-035 changes how that list is ordered.
- **A chained run leaves exactly one output folder.** The advisor service names its own run directory after the domain (`cs-ai-ml_<run_id>`), and only the pipeline knows the chosen topic, so `run_advisor_then_pipeline` renames that directory to `<topic-slug>_<run_id>` once `select_topic` returns, before starting `run_pipeline`. `run_pipeline` then opens the existing directory and re-writes `00_trend_advisor/result.json` with `chosen_topic` populated, so Stage 0's evidence and the four stages' artifacts share one auditable folder. `run_trend_advisor_stage` alone is unaffected and keeps its own domain-named directory — stopping at the shortlist (user story 10) still leaves a self-contained folder. The rename is skipped unless the reported directory exists and its name ends in `_<run_id>`, so a caller-supplied or test-substituted advisor reporting some other path is never moved. **Found by review, not by the tests:** the first implementation wrote two folders per chained run, and the three fake-service tests could not see it because a fake that writes nothing to disk cannot catch a directory bug. The regression test now loads the real advisor service and stubs only its two external dependencies (`find_rising_topics`, `llm_provider.health_check`), asserting on what actually lands on disk.
- **The advisor service is loaded on first use, not at orchestrator import,** unlike Services 1-4. Its `service.py` imports the gap-mining swarm and the local-model adapter and mutates `sys.path` at import time. Stage 0 is optional, and a plain four-stage run must not pay for — or be broken by — a stage it never invokes. It still goes through the same `_load_service` helper under a unique module name, so the module-name-collision rule (D-010/D-012/D-013) still holds.
- **Tests:** three new fake-service tests in `tests/orchestrator/test_pipeline.py`, matching the existing fake-service pattern: the standalone stage's event shape, ordering and `run_id`; the chained path (topic reaches `research_question`, `chosen_topic` reaches both the result and `metadata.json`, Stage 0 events precede Discovery); and the no-pick path starting no pipeline. No existing assertion or fixture was modified — the ticket's own criterion was that the four-stage path stay provably unchanged.

## D-035 — arXiv is a second candidate source, merged by normalized topic, and only ever breaks growth ties
- **Date:** 2026-09-13.
- **Problem:** arXiv previously contributed a single integer per OpenAlex topic and nothing else. No preprint could become evidence a student could read, and cross-source duplicate topics were structurally impossible rather than deliberately merged — the candidate set came from OpenAlex alone, so there was nothing to merge.
- **Decision:** `velocity._arxiv_candidate()` now returns a `TopicCandidate` carrying real preprints as `ExamplePaper`s, and `velocity.merge_sources()` folds it into the OpenAlex set on a normalized topic key. A topic both sources found stays **one** shortlist entry keeping OpenAlex's `paper_count`; the two counts are never summed, because OpenAlex counts an indexed corpus while arXiv returns a relevance-ranked sample of 50 — adding them would report a volume neither source measured. Example papers union with title-level dedup, so a preprint OpenAlex has since indexed is not listed twice. Still gated on `ARXIV_DOMAINS`, so non-CS-adjacent domains are untouched and remain OpenAlex-only. `_arxiv_candidate` reports `paper_count=0` and carries its sample only in `arxiv_recent_count`: setting both to the same number double-counted the sample in the ranking key and also put a sampled figure in the CLI's "Recent papers" column and in `is_crowded`, where the student is owed OpenAlex's measured count. Both sources filter on the same 3-year window with the current year excluded — the arXiv side originally had no upper bound, giving it a 4-year span that was then summed against OpenAlex's 3.
- **`MIN_TOPICS_FOR_SHORTLIST` is re-checked after the merge.** Collapsing near-duplicate topic names onto one key can drop the shortlist below the floor that exists so a too-thin result fails loudly; without a second check the merge could quietly under-deliver.
- **Rejected: a combined growth×gap score for the final ranking.** Two reasons. `TrendAdvisorResult` has no field to persist such a score, so the number that decided the order would be invisible in `result.json` — precisely the unverifiable output this stage exists to avoid. And the student-facing promise is that growth is `recent ÷ prior` and can be re-derived by hand; arXiv's count is a sampled top-50, so letting it into that ratio would break the promise. `service.py`'s gap-first / velocity-second stable sort is therefore unchanged, and `arxiv_recent_count` instead joins the **volume** half of the growth key (`velocity._growth_key`), where it means "more recent work across both sources" and can reorder equal-growth topics without ever entering the ratio. Ranking stays pure arithmetic over real counts; no model is asked what is rising.
- **Gap mining reads the new papers because the merge interleaves them.** The first version of this entry claimed preprints "fill in for free wherever an OpenAlex paper has no retrievable text". That was false, and review caught it: the swarm's `_worker_papers` takes the first `MAX_PAPERS_PER_TOPIC` (2) example papers that have text, and *every* OpenAlex paper has text because `works_for_topic` filters on `has_abstract:true` — so appending arXiv's papers after OpenAlex's put them permanently out of reach. `merge_sources` now interleaves the two sources' example papers, so a topic found by both spends one of its two worker slots on a preprint. `merge_sources` still knows nothing of `MAX_PAPERS_PER_TOPIC`; interleaving is an ordering, not a cap. No change to `gap_mining.py` or `service.py` was needed. The regression test asserts on the worker *prompts*, not on list contents, because list membership was exactly what the false claim rested on.
- **The arXiv-only-topic path is dead in production, and is recorded as such rather than described as a feature.** `_arxiv_candidate` is always queried with an OpenAlex topic name, so every arXiv candidate normalizes onto an existing key; a topic reachable only through arXiv cannot arise from `find_rising_topics`. `merge_sources` still appends unmatched secondary topics rather than dropping them, so the function is correct in isolation, but nothing in the current pipeline exercises it.
- **Tests:** the criterion test is `test_a_topic_found_in_both_sources_is_merged_not_double_counted` (`tests/services/test_trend_velocity.py`), plus same-paper title dedup, arXiv-only topic survival, an end-to-end CS-domain merge, and `test_arxiv_volume_breaks_a_tie_between_equally_growing_topics` pinning the tiebreak semantics. A `arxiv_recent_count is None` assertion was added to the MECHANICAL test so "non-CS domains never query arXiv" is pinned at unit level rather than only at service level.

## D-036 — The trend-advisor smoke runner exits non-zero when no usable question is drafted, rather than falling back like the CLI does
- **Date:** 2026-09-13.
- **Decision:** `scripts/smoke_test_trend_advisor.py` now drives the CLI's own code path — `parse_pick()` against the live shortlist instead of hard-coding `shortlist[0]`, a real `_research_question_for()` call, and both hand-off branches — and exits 1 when no usable research question comes back, printing which of the two failure modes occurred: the provider was unreachable (its own message is shown), or the provider answered with an empty or unparseable reply. They have different causes and different fixes, so collapsing them into one message would cost a human the diagnosis. The reply is stripped first, so a whitespace-only answer counts as unusable rather than becoming a blank question the pipeline then runs on.

The `except LLMProviderError` guard covered only the unreachable case; a provider that answered with nothing usable silently substituted the bare topic name, ran the whole downstream pipeline on it, and exited 0 — a false pass for a flow whose question-drafting step never worked. The fallback is gone.

A manual runner has nobody to correct it, so the same fallback would report a pass for a flow that never drafted a question — the exact fabricated-confidence failure D-033 already caught once with the "no recurring gaps found" message.
- **Observed on the verification run (Ollama not running):** live OpenAlex returned 8 ranked CS/AI/ML topics with real DOIs and saved them; arXiv was unreachable and gap mining was skipped, both surfaced as explicit warnings; `parse_pick("go with #1")` resolved correctly; the guard then fired and the runner exited 1. The hand-off block needs the same model, so it was verified by wiring rather than executed — a fully green run of this script requires `ollama serve`.

## D-037 — The advisor CLI degrades gracefully where a human is watching; the unattended runner never does
- **Date:** 2026-09-13.
- **Decision:** `advisor_cli` now guards both of its local-model calls. A provider failure inside the converging chat (`_chat_turn`) prints the provider's message and keeps looping, stating explicitly that the shortlist and its evidence are still there. A provider failure — or an empty/malformed draft — at the question-drafting step after lock-in prints what happened, then pre-fills the existing "use this, or type your own" prompt with the chosen topic under an explicit *this is your topic, not a research question* warning.
- **Why this diverges from D-036 on purpose:** graceful degradation requires a human to degrade to. The student at the prompt has already paid minutes of live OpenAlex queries and gap mining, so killing the CLI with a traceback throws away real work they cannot get back cheaply; and they can edit a draft by hand. The unattended smoke runner has nobody to correct it, so the same fallback there would report a pass. The asymmetry is the point, not an inconsistency.
- **The silent path was closed too:** `_research_question_for` returns `""` on a malformed reply, which the previous `or chosen.topic` swallowed without a word. It now routes through the same announcement, so the student can always tell whether a model drafted the question or not.
- **A bare Enter can no longer lock in a topic the student never picked.** Two compounding defects, both found by review. `parse_pick`'s verb alternation matched mid-sentence, so ordinary questions parsed as picks — not only the `do 3` case that was reported, but every pick verb: `should I pick 2 or 3?`, `is option 2 crowded?`, `would 2 take 3 years?` all resolved to a number. And the lock-in used `Confirm.ask(default=True)`, so a reflexive Enter accepted it. A string ending in `?` or opening with an interrogative can now never match a *numeric* pick pattern (exact topic-name matching stays reachable, so a title beginning with such a word still works), bare `do` is replaced by `let'?s\s+do`, and the confirm defaults to `False`. This stage's whole premise is that the topic choice is an explicit human decision; that path silently violated it.
- **Known residual:** a non-question statement containing a verb and a number (`it might take 2 years`) still parses as a pick. The `default=False` confirmation is the backstop, and the pick is always shown before it is accepted.
- **Tests:** `tests/researchgenie/` covers each of the above — the chat blip leaving the shortlist intact, the honest post-lock-in fallback, the empty-draft announcement, questions containing pick verbs not parsing, statements still parsing, and the confirm's default (56 passed, up from 47). `parse_pick` remains pure deterministic matching with no model call, so "go with #2" means the same thing on every run.

## D-038 — Four Trend Advisor acceptance criteria were true in the code but asserted nowhere; each is now pinned by a test that fails on its regression
- **Date:** 2026-09-13.
- **Decision:** The seven Trend Advisor tickets were audited criterion by criterion against the code rather than against the previous commit's summary of it. Six tickets were fully met. ## D-039 — Discovery's retrieved Discussion/Future-work text now reaches Writing, closing the evidence-depth bottleneck D-029 localized
- **Date:** 2026-09-13.
- **The issue, as D-029 left it.** Discovery already fetches each candidate paper's real Discussion/Limitations/Future-research sections (`discovery/fulltext.py`, Europe PMC JATS then an open-access PDF) for its own gap mining, and then dropped every character of it: `Paper.to_client_dict()` exported only `has_fulltext: bool`, so `PaperMetadata` had nowhere to carry the text and `writing_prep.write_literature_files()` passed `paper.abstract` alone. D-029 quantified the consequence rather than asserting it — across §17's 4 real runs, **0 of 16 sections reached even half of their own maximum word budget**, so the writer is never output- or prompt-limited, only evidence-limited — and named this the "definitive, evidence-backed candidate for a future, dedicated pass." This is that pass.
- **Where the text is picked up, and why not in `to_client_dict()`.** The `corpus` event is emitted *before* the full-text stage runs, so `to_client_dict()` is built when `future_text` is still `None` for every paper. Rather than re-emit the corpus or reorder the stages (both visible to the TUI and its tests), the existing end-of-stage event carries the text: `fulltext_done_event()` now returns `excerpts: {paper_id: text}` alongside the `paper_ids` it already reported, and `service.py` merges it in by id. One new event field, no ordering change. The event stays internal to the service: `orchestrator/pipeline.py::_adapt_inner_event()` keeps only `{"raw_type": ...}` in `details`, so no excerpt text reaches the SSE progress stream. It does reach `GET /research/runs/{run_id}`, which encodes the whole `PipelineResult` — that response grows by the retrieved text, as it already did for abstracts.
- **`evidence_depth` gained a third value rather than reusing `full_text`.** What Writing now receives is the abstract plus the authors' own closing sections — more than an abstract, and genuinely less than the paper: no methods, no results tables, no related work. Declaring it `full_text` would have let the card builder describe a source as reviewed in full, which is the exact dishonesty the existing `abstract` depth was added to prevent; declaring it `abstract` would have told the model to ignore the new text ("extract only claims explicitly stated in the abstract"). So `abstract_plus_discussion` exists, the two retrieved parts are written under their own `## Abstract` / `## Discussion, Limitations, and Future Work` headings so the model can always tell which it is reading, and the prompt's standing prohibition on claiming a full-text review is repeated verbatim under the new depth.
- **Service 4 had to change in the same pass, or this fix would have made its scores worse.** `build_reference_profiles()` builds each reference's evidence profile from `title + abstract + venue`, and `find_unsupported_claims()` flags any cited sentence that does not overlap it. A claim correctly drawn from the Discussion excerpt overlaps the abstract barely at all, so every such claim would have been reported as unsupported — the same false-positive class as D-021, and it would have arrived as a *regression in the quality score* caused by giving the writer better evidence. The profile now includes `discussion_excerpt`, so Service 4 checks against exactly the evidence Service 2 was given. A test pins both directions: a Discussion-sourced claim passes, and two unsupported claims are still caught — a wholly unrelated one and, more to the point, a same-field claim about a population and outcome the paper never studied. **The trade-off is real and accepted knowingly:** a profile carrying a 7,000-character excerpt holds several times the tokens of title+abstract, so against the unchanged 3-token overlap threshold this check now clears more claims than it did. That is the price of not reporting every correctly Discussion-grounded claim as unsupported. The threshold is deliberately left at 3 rather than retuned in the same pass on a guess — revisit it with real-run data.
- **A paper with no abstract is no longer discarded.** `write_literature_files()` skipped any paper failing `paper.abstract and paper.has_abstract`, which would now have thrown away a real 7,000-character Discussion section over a missing abstract. Papers with neither are still skipped — metadata alone gives the card builder nothing.
- **The resource cost was computed, not assumed (D-030's precedent).** The card call runs at `max_tokens=8000`, and `_context_window_for` selects a tier from `max(prompt_chars // 4, max_tokens)`, so the prompt has real headroom before the next tier. What is pinned is the **margin**, because there is no fixed payload to measure: the card payload's tag definitions carry `description`/`include_when` prose that is itself LLM-generated (`tag_semantics.py`), and no real card artifact survives under `outputs/` to measure one from. The margin is exact — at `max_tokens=8000` the 16,384 tier holds any prompt up to **33,539 characters**, and the card's own 3.6 KB system prompt plus a full-size excerpt (`fulltext.MAX_SECTION_CHARS = 7000`) spends only 10.6 KB of it, leaving ~23 KB for tag definitions, metadata and the abstract. The excerpt is therefore paid for out of headroom that already existed. Unlike D-030's rejected `max_tokens` increase, this costs zero additional VRAM. A test pins the tier so a future prompt growth that crosses it fails loudly instead of silently slowing every card build.
- **Real verification, live and model-free.** The full-text route needs no LLM, so the central claim was checked against the live APIs rather than only against fakes: a real Europe PMC article returned **7,005 characters** of genuine Discussion text, which flowed through `fulltext_done_event` -> `PaperMetadata.discussion_excerpt` -> the literature file, producing a **7,265-character evidence packet against the same paper's 176-character abstract-only packet — 41x**. The registry read it back as `abstract_plus_discussion`. Left behind as `scripts/smoke_test_evidence_depth.py` (network, no model) so the claim is re-runnable rather than a number in a log; it exits non-zero when no full text is retrieved, so a network failure cannot read as a pass. Real full-text prose is never ASCII (that fetch returned en-dashes and non-breaking spaces), so the UTF-8 write / UTF-8-sig read round trip is pinned by its own test.
- **Tests:** 15 new (`tests/services/test_evidence_depth_forwarding.py`), one per link of the chain — contract field and its JSON round trip, the event, the adapter, **the merge inside `run_discovery` itself**, the literature file, both skip rules, the registry accepting the new depth and still rejecting an unknown one, the prompt, Service 4's profile, the encoding round trip, and the context tier. The merge test exists because review caught its absence: unit-testing `fulltext_done_event` and `_paper_metadata` separately cannot detect a wrong dict key or a lost id, since the excerpts arrive on a later event than the corpus and are matched back by paper id — exactly the link that fails silently. It was falsified rather than assumed, per D-038: disabling the merge makes it fail. Full suite **303 passed, 3 skipped, 0 failed** (up from 288), no regressions.
- **Found by review, not by the implementation.** Two things in this pass were wrong until the code review caught them, and both are recorded rather than quietly fixed. First, the new test file did a bare `import service`, so it bound whichever pipeline service another test file had imported first — the full suite was green only by collection order, and running it next to `test_writing_prep.py` failed. It now loads each service by path under a unique name, and was re-run in both orders. This is the exact collision `orchestrator/pipeline.py::_load_service()` exists for, and it recurred anyway. Second, the one genuinely new seam — the merge inside `run_discovery` — had no test at all, while this log already claimed every link was pinned; the unit tests for `fulltext_done_event` and `_paper_metadata` could not have caught a wrong dict key or a lost paper id between them.
- **Not claimed.** Ollama was not running on this machine during this pass, so **no full end-to-end pipeline run was executed** and the actual effect on drafted paper length is **unmeasured**. D-029's analysis predicts an increase, the evidence packet is demonstrably ~30x larger for a paper with a retrieved full text, and every link is pinned by a test — but the headline number (average words per draft) must be measured by real runs before it is reported. That measurement is the next step, not a result of this one. Also unchanged: how many papers per corpus actually have an open-access full text is whatever `fulltext.is_candidate()` and the live sources yield, historically a minority, so corpora where nothing is retrievable behave exactly as before.

## D-042 — The automatic Ollama install timeout was too short for the package it installs, and a timeout was reported as a flat failure
- **Date:** 2026-09-13.
- **Problem (found by running the mock-only path on a real, clean machine for the first time):** `TILL_NOW.md` listed the Windows `winget`/macOS `brew` install path as "verified only via mocks (this dev machine already has Ollama; no Windows/macOS machine without it was available)". Run for real on a machine with no Ollama, `attempt_automatic_install()` failed: `winget install failed: Command '[...]' timed out after 600 seconds`. The cause is not the machine — `winget show --id Ollama.Ollama` reports `OllamaSetup.exe` v0.34.0, and a HEAD against its release URL measures **1501.3 MB**. Finishing a 1.5GB download inside 600s needs a sustained ~2.5 MB/s with *nothing* left over for winget's source refresh or for Inno Setup to unpack and install 1.5GB. The old value could not succeed on an ordinary connection: a direct ranged download from that same release URL on the test machine measured **1.92 MB/s**, a perfectly healthy link, which puts the download alone at **~13 minutes (780s)** — already over the 600s budget before winget's overhead or Inno Setup unpacking a single file. A mock never downloads anything, which is exactly why every existing test passed: `test_attempt_automatic_install_on_windows_with_winget_runs_it` stubs `subprocess.run` as `lambda *a, **k: _Result()`, discarding the `timeout` kwarg that was wrong.
- **Decision:** one shared module constant, `INSTALL_TIMEOUT_SECONDS = 3600`, used by both the winget and the brew call. Sized to be about the connection rather than the clock: 1.5GB at a slow-but-real 1 MB/s is ~25 minutes of download before installation starts.
- **Second, separate fix — a timeout is not a failure.** Both branches caught `OSError` and `subprocess.TimeoutExpired` together and rendered either as `"<tool> install failed: ..."`. But a timeout means *not finished yet*, not *this machine cannot install Ollama*; a user on a slow link would abandon a download that was progressing perfectly well. `TimeoutExpired` now has its own branch and its own message (`_timeout_message()`), naming the ~1.5GB download as the likely cause, saying the attempt may have been fine, and giving the direct download URL. `OSError` keeps the original wording.
- **Rejected: removing the timeout entirely.** An unbounded `subprocess.run` turns a wedged package manager into a hung CLI with no way out; the timeout exists for that, and the bug was its value, not its presence. **Rejected: an env-var override.** No evidence anyone needs to tune this, and a constant is equally overridable from a test.
- **Tests:** 4 new in `tests/researchgenie/test_ollama_manager.py`, all of which fail against the old code: the constant clears a 1800s floor derived from the measured installer size; the winget and brew calls each pass that shared constant (asserted through a `subprocess.run` fake that *records* its kwargs instead of discarding them, the gap that let this through); and a `TimeoutExpired` is reported as a timeout with somewhere to go. 320 -> 324 tests.
- **Scope note:** this fixes the reporting and the budget, not the download. The real install on the test machine still took longer than the old limit allowed — which is the evidence for the new one.
